# A repo that adopts a plugin-enforced convention can enforce it without the plugin

## Context

Some conventions here produce a file that every contributor to an adopting
repo has to keep current. The first is a record directory's `INDEX.md`. It is
generated by `scripts/dev-docs-layout.py --write-index`, and check 9 fails
while it is stale. That script ships only inside this plugin.

That is fine while every contributor runs the plugin. It breaks in a shared
repo where they do not. When a teammate without the plugin adds a record, the
index goes stale and they have no way to regenerate it. Their local tooling
does not report it either. `actions/dev-docs` is the only route that reaches
them, and it runs only on GitHub Actions, depends on this repo at `@main`, and
reports the problem only after the push. A team repo adopting the decisions
index hit exactly this case (#133). Most of its contributors don't use the
plugin, and the fix there was to copy a generator for decisions only into the
repo, with a test.

`2026-09-19-comment-key-check-belongs-here.md` puts enforcement in the repo
that owns the convention. That holds for a check that fires while a session
writes, which the plugin's hooks reach in every repo. It does not hold for a
file in the adopting repo's tree that its own contributors must be able to
regenerate. There, a check only the plugin can run leaves everyone else stuck.

## Decision

A convention whose enforcement lives in this plugin, and that leaves a
file in an adopting repo's tree, must be maintainable in that repo
without the plugin. The plugin's implementation is the reference. A repo whose
contributors all run the plugin calls it as before. A repo where some don't
carries its own generator and check, in its own language and tooling, wired
into its own suite. The plugin's check must accept the vendored generator's
output. Wherever the plugin's output names its own tool, it allows the
adopting repo to name its tool instead. For `INDEX.md`, that is the header
comment's regenerate command, which check 9 and `--write-index` both keep. The
canonical files a repo copies name no plugin script, so a copy does not point
contributors at a tool they lack.

## Consequences

- Good, because a contributor without the plugin finds a stale index with the
  repo's own check, before the push, and regenerates it with a command the
  repo actually has.
- Good, because a contributor who does run the plugin sees the same file pass,
  so the two routes agree rather than flip a header back and forth.
- Good, because the conventions stay adoptable by teams, not only by
  repos whose every contributor has installed this plugin.
- Bad, because a vendored generator is a second implementation that can drift
  from the reference. The plugin's check catches drift in the output only when
  someone runs the plugin against that repo.
- Bad, because the header becomes trusted input: it is free text echoed into
  the failure message, though never executed.

## Revisit when

- Vendored generators drift from the reference often enough to warrant
  shipping a copyable, standalone renderer with a version line to compare
  against (#133's optional item 3).
- A convention whose output cannot name its tool needs the same treatment,
  which would need another way to tell the plugin's check which output to
  accept.

## Confirmation

Check 9 in `scripts/dev-docs-layout.py`, with the vendored-header cases in
`dev-docs-layout.test.sh`: an index naming another generator passes, keeps its
header through `--write-index`, still fails when its table is stale, and fails
when the header changes anywhere but its command. The rule for later
conventions rests on `dev_docs_layout.md` and review.

## Alternatives

- **Require every contributor to install the plugin:** the adopting team does
  not control that, and it is the case that failed.
- **Rely on `actions/dev-docs` in CI:** GitHub Actions only, pinned to this
  repo's `@main`, and it reports after the push without giving the contributor
  a way to regenerate.
- **Ship only a standalone renderer to copy:** still a second copy to keep
  current, and in Python, which not every adopting repo runs. It can be added
  later without changing this rule.
